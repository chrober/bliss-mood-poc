# Phase B: RAM-gated nonmonotonic online worker autotuning

**Status (28 October 2026): experimental opt-in implementation in `feat/ram-safe-online-autotune`, stacked on PR #18. NOT a validated production scheduler or proof of an optimum.** The previous resource-threshold controller is unchanged and selected by default.

## Design intent

The goal is **one adaptive strategy which discovers effective concurrency on its actual host and workload**, not a Ryzen-specific fixed-worker recommendation. The existing 100-song/3-model native C++ benchmark gave median 6=70.98, 8=70.42, 10=63.75 and 12=88.17 songs/minute (two repeats). That is a **nonmonotone observed throughput curve**, with possible environmental noise. A hill-climbing rule that abandons higher counts after a worse point is unsuitable. No claim of causality, universal optimum, or safe fixed-twelve default follows.

Separate mechanisms:

1. **Admission safety / resource governor:** use the CPU capacity permitted to the process as a hard upper bound (maximum 64) and measure available memory before starting. Compute a conservative initial reserve, here `max(512 MiB, 10% of initially available memory)`, and charge **at least 256 MiB estimated incremental memory per added worker**. Reduce the preferred initial concurrency if its estimated budget would be exceeded, rather than assuming `--workers auto` is always safe. Require valid free-RAM telemetry on every completion, **and run an independent 250-ms memory watchdog while a song is in flight**. A missing/invalid sample or a breached reserve is a terminal safety fault: the watchdog signals native IPC cancellation, the coordinator stops dispatch and checks its guard during 200-ms result waits, and the owning Rust threads kill/reap their native Essentia child processes (rather than killing bare PIDs). A completion-driven failure also signals cancellation immediately. On lesser headroom pressure, the online tuner reduces concurrency instead of launching additional sessions. Raise the incremental-memory estimate whenever observed host/cgroup memory depletion implies higher costs; never relax the estimate within that scan. These **provisional guardrails** are portable heuristics to test, **not a guarantee against OOM**. The watchdog is independent of song completions but still samples periodically, so rapid allocations can exceed its margin between polls. Native C++ IPC can be cancelled promptly using the owning Child handle; already-running Rust ONNX computation is **not** preemptible yet. The current design cannot guarantee that an operating system or cgroup OOM killer will not intervene first. Failures may leave a *partial, private* sidecar rather than silently continuing.

2. **Online throughput exploration:** an ordered **coarse candidate schedule** includes minimum, initial, maximum and evenly spaced intermediate worker counts, with no assumption of monotonicity. Each candidate needs at least eight successfully completed songs and twelve seconds of data before a probe is accepted. Score is analyzed EffNet patches/second, alongside songs/minute, rather than raw CPU load (which is not a throughput objective). The initial coarse sweep proceeds through the safe candidates even across a throughput trough; the **second sweep runs in reverse order**, including a genuine second probe for a candidate which is already active at the sweep boundary. This reduces systematic time drift and supplies a second observation per feasible candidate before ordinary exploitation. Unsafe candidates may be memory-gated, so two samples are **not guaranteed**. A **bounded rolling median** of up to eight recent probes per worker count replaces single-best-window selection. After the first sweep, a solitary surprising new score cannot displace a previously observed incumbent without replication. Explore higher candidates even after a lower candidate performs worse. Use a 5% improvement margin when selecting the best observed candidate, to limit insignificant switches. For longer scans, return to the best observed candidate between budgeted re-exploration rounds. Each candidate is separately RAM-gated. The controller adjusts only the **in-flight dispatch cap**; native/ONNX sessions are persistent and never restarted for re-sizing. **Every change now drains the prior configuration's in-flight jobs before admitting new work.** The measurement epoch starts *after* this drain, so completions dispatched under an earlier capacity cannot contaminate the new capacity's probe. This improves attribution, but model warmup, changing songs, temporary idling and the overhead of draining still affect total end-to-end completion time.

3. **Diagnostics:** the existing `diagnostics.adjustments` and `diagnostics.controller_decisions` belong to the legacy policy. Experimental observations live under `diagnostics.online_autotune`: actual starting/final workers, retained coarse probes and worker adjustments (maximum **256 each** for bounded full-library output), RAM reserve and worker estimate, candidate changes with available RAM, and probe/safety counters. Per-candidate rolling evidence includes sample count, median and observed min/max patch rate. `search_completed` means every candidate was sampled at least once; `replication_completed` additionally requires two retained samples each; `observed_ranges_separated` is a **descriptive** test requiring the winner's observed minimum to exceed every competitor's observed maximum by over 5%. These are **not formal statistical confidence intervals or guarantees of the true optimum**; `best_tested_workers` is the current highest-ranked sampled candidate.

## Invocation (experimental)

```text
bliss-mood scan-features ... --workers auto --adaptive-workers \
  --adaptive-policy autotune --min-workers 1 --max-workers auto \
  --threads 1 --priority normal --json
```

Windows `--priority normal` is only for explicitly controlled comparisons; omit it for portable Linux usage. Use an explicit bounded `--max-new`, a fresh sidecar, and matching model/native worker versions for research. The legacy mode remains `--adaptive-policy resource` (default), with the existing minimum-song gate and 20-second cooldown.

Linux free RAM now combines `/proc/meminfo` with **visible nested cgroup ancestry**: it parses the process's unified v2 or legacy memory-v1 membership from `/proc/self/cgroup`, walks accessible ancestors under the standard `/sys/fs/cgroup` mounts, and uses the **smallest visible remaining memory headroom**, not merely the host-wide figure. A unit test checks the namespace-root path and rejects traversal. This is **not yet a full cgroup namespace/mountinfo resolution**: custom mount roots, unavailable ancestors, swap quotas, CPU throttling and macOS remain unhandled. Where free RAM cannot be read, `autotune` refuses to begin. Tests must cover cgroup variation, failure handling and 4-GB Raspberry Pi constraints before enabling it by default.

## Why this is only Phase B groundwork

- **A short scan cannot identify an optimum.** Coarse candidates can remain untested; no success claim is allowed. The extra initialization cost of rarely used ONNX sessions can hurt short-job throughput.
- A fixed-duration window over *different songs* and NAS caching does not give a statistically comparable experiment. The two balanced sweeps and bounded rolling medians reduce sensitivity to some timing artifacts, but do not establish exchangeable, randomized or independent samples. Patch count is a useful denominator, but decode cost, song complexity and ambient interference vary. **The new drain boundary prevents mixing old and new admission caps, not confounding from the song mix.** Do not mistake a single 5% margin for statistical significance. Moreover, measuring probes after drain excludes switching overhead from the scored patch rate; validate actual full-scan wall time as an independent goal.
- **Implemented:** independent watchdog at ~250 ms, coordinator polling at ~200 ms on outstanding completions, explicit native IPC cancellation and child reaping on a memory fault, and additional `diagnostics.memory_watchdog` with sampled low-water RAM. **Cancellation is now scoped to a single scan** (shared `Arc<AtomicBool>` propagated from the watchdog to the scan's worker threads, native Essentia IPC, and ONNX analysis engine); no process-global flag can inadvertently cancel a different scan. The native transport checks it during each ≤200-ms blocking wait, and the Rust frontend checks at entry, after decoding/preprocessing, before/after encoder and classification calls, between patches, and around hashing/persistence handoff. A deterministic test exercises independent watchdogs, and a fixture-backed test triggers cancellation while a real mock C++ worker is blocked in IPC, verifies reaping, and checks that an unrelated worker still processes a request. **Still missing:** preemption of a single already running ONNX Runtime call, safe interruptible FFmpeg child-process decoding and model-session initialisation, measured per-session allocation accounting, full cgroup OOM event inspection, sub-poll allocation protection, and a platform-tested hard stop for in-flight nonnative computation. The new stage checks are cooperative and must not be described as guaranteed immediate interruption or OOM protection.
- The candidate spacing is provisional and can miss narrow peaks. Explore/refine adaptively with paired/interleaved comparisons, repeated probes, recency-aware confidence estimates and change-detection, while charging search cost. Resource isolation must always dominate optimization.
- Benchmark *completed-song throughput* and *time-to-finish* along with patches/sec on long, heterogeneous bounded cohorts and on differing host budgets. Synthetic tests must include 6→8→10→12 with a local trough, increasing monotone, decreasing, flat/noisy, changing workload, and low-RAM situations. Verify strict classification / embedding parity with the original native C++ frontend.
- Test on CPU-constrained containers and ARM/4-GB machines before generalizing. Defaults must remain stable and fail safe; PR #16 similarity work and original library/Bliss DB stay untouched.

## Next implementation gates

1. Make CI Rust tests/Clippy and native smoke green for **exact** Phase B code head; add CLI integration and failure-mode tests.
2. Confirm CI for the new scan-local cancellation tests (including the blocked native C++ fixture); develop an out-of-process or otherwise safely interruptible boundary for a single ongoing ONNX invocation, FFmpeg child decoding, and model initialization. Continue nested cgroup/macOS validation and test memory pressure on the actual target platforms.
3. Improve online measurement beyond the implemented forward/reverse repeated coarse sweeps: use randomized/interleaved candidate windows, robust uncertainty estimation and change detection, explicitly accounting for exploration overhead and remaining scan size.
4. Exercise a mixed-duration, private local manifest with no raw private data committed. Compare to best safe fixed setting **per host** solely for validation; no host-specific tuning rules.
5. Only after cross-platform, RAM pressure, throughput and parity validation consider making autotune the default.
